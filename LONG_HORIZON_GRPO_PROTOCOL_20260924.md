# Eight-step semantic GRPO: three experiments, code ready / no new runs

The server was off when this code was prepared. These are runnable protocols,
not observed results. The old 54-trajectory open-loop capture and fixed-P1
offline LoRA run remain side diagnostics and cannot answer this question.

## 1. Frozen-policy trajectory census

Run the pinned 1.5B policy for eight fresh q-valid tasks × 16 trajectories ×
8 edits. P0 and every edit receive public tests; the next prompt sees the
preceding public feedback. The model never sees q. A single network-blocked
Modal sandbox and injected checkout are reused for all trajectories of one
task. The worker fails if tests/probes mutate other repository files.

After capture is **complete**, measure all nine P0–P8 q values offline, using
one sandbox per task and one transfer of that task's 256-case bank. Identical
task/source states are measured once. The summary reports within-task
variance of `Y8`, `Y8 + 0.5 p8`, and `Y8 + 0.5 q8`, including the number of
tasks whose Test group is tied but Semantic group is informative. It also
records how often q changes before public p and moves while p/Y are silent.
The task is the coverage unit, not 16 independent tasks or dependent pairs.
The canonical entry is
[`run_swesmith_trajectory_pipeline.py`](scripts/run_swesmith_trajectory_pipeline.py),
with [`swesmith_closed_loop_8x16x8_v01.json`](configs/swesmith_closed_loop_8x16x8_v01.json).
No census result has been generated by this corrected code.

## 2. On-policy whole-trajectory GRPO: two matched arms

Use the frozen 20 train / 8 held-out task split and pinned 1.5B rank-16 LoRA
base. For each update, one train task supplies a group of 16 **fresh** complete
eight-edit trajectories from the current policy. Both arms get identical
public feedback and use the same task order, seeds, generation cap, optimizer,
and rollout budget. The only reward distinction is:

```text
Test:     R_i = Y8_i + 0.5 p8_i
Semantic: R_i = Y8_i + 0.5 q8_i
```

The Semantic arm computes q8 only after all 16 trajectories are generated;
no q is returned to the policy. Normalize the 16 trajectory rewards within
the task; repeat each trajectory's single advantage across its eight actions.
Tied groups have zero advantage and skip the optimizer update. This tests
**inter-trajectory** reward resolution, not which edit within a trajectory
deserved credit. At updates 0, 5, 10, 15, and 20, evaluate one deterministic
eight-edit rollout on each held-out task. The metric is held-out
`public_test_solve_at_8` versus consumed training trajectories/environment
steps. Here `Y8` is the official selected public-test pass gate, **not** an
independent hidden SWE-smith grader outcome. Paired task-level comparisons
and uncertainty are required before claiming an advantage.

Run the arms separately through
[`train_swesmith_long_horizon_grpo.py`](scripts/train_swesmith_long_horizon_grpo.py)
with [`swesmith_long_horizon_grpo_v01.json`](configs/swesmith_long_horizon_grpo_v01.json)
and `--arm test` or `--arm semantic`. Do not reuse a previous arm's output
directory or frozen P1 actions. This code has not run on the GPU/Modal setup.

## 3. Conditional step-wise extension

Only after reviewing experiment 1 and the whole-trajectory comparison, the
same trainer has an explicit `--credit stepwise --pilot-summary <summary.json>`
mode. For potential `v_t` (`p_t` or `q_t`), the per-action return-to-go is

```text
G_t = Y8 + 0.5 (v8 - v[t-1]),     t = 1,...,8.
```

Normalize `G_t` across the 16 trajectories separately at each step. This
tests intra-trajectory credit and is **not** part of the primary two-arm
experiment. The Semantic step-wise mode measures q0–q8 after generation;
the policy still sees only public feedback. Requiring an explicit pilot
summary prevents accidentally promoting the optional extension to a result.

This design removes per-state sandbox startup, but still runs public tests at
each state and trains on 128 generated actions per GRPO group. Runtime must be
measured; no ten-minute completion claim is made.
